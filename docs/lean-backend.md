# MC-004 — Lean process adapter (initial implementation)

The adapter checks an exact `.lean` entrypoint against the manifest's source digest and checked source inventory, hashes the configured executable, and checks externally supplied approved backend and policy digests. It then calls a runner with an argument list, a fixed working directory, and no shell interpolation. Standard output, standard error and the process exit code become **candidate evidence** in the MC-003 registry. A nonzero exit code remains a recorded failure.

`SubprocessRunner` requires an owner-provided sandbox command prefix, uses a minimal environment, a timeout and a post-execution output-size check. Its `environment_bytes` encode its prefix, timeout, output limit and subprocess environment; the manifest's environment pin must match those bytes. Its prefix must be separately reviewed and configured to deny network access, ambient secrets and unauthorized filesystem access. The library cannot establish whether an arbitrary prefix actually isolates the process. It currently buffers output before checking size; deployment must also impose an external output/disk budget.

No Lean executable is installed in the local test workspace. The tests use an injected fake runner, so they verify preflight decisions and evidence recording, **not** Lean kernel compilation. The adapter does not prove that its source inventory contains all imported modules; it does not verify the source repository identity, the external policy approval, an axiom report, an independent replay or the semantic fit of a theorem. Those are gates for later integration. `CandidateEvidence` is not an accepted receipt or a mathematical certificate, even when `returncode == 0`.

The configured digest must be owned by a trusted administrator rather than copied from the producer's proposal. An execution deployment should use a pinned Lean toolchain and a source/import closure whose bytes and repository pins are independently authenticated before relying on the process result.
